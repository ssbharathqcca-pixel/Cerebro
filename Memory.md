A preferred reasoning format for complex work is:

## 2.2 Cognitive-load constraints

Roi has explicitly described ADHD/executive-function friction, task paralysis, procrastination, and perfectionism as important workflow constraints.

Therefore:

- Break work into executable chunks.
- Reduce decision fatigue.
- Identify the immediate next action.
- Separate **must do now** from **later**.
- Avoid giving a giant unordered backlog.
- When several actions are necessary, establish dependency order.
- Prefer automation/checklists/gates over relying on willpower.
- Avoid repeated questions when the answer already exists in context.
- For difficult tasks, make a best-effort completion rather than stalling on minor ambiguity.

- Claiming something was done when it was not.
- Pretending a tool was used when it was not.
- Fabricating sources, tests, outputs, or confidence.
- AI agents pasting code/JSON into chat instead of editing the requested files.
- Models refusing to let Roi inspect or touch generated work.
- Overconfident model capability claims.
- Excessive prose when an artifact or direct answer is needed.
- Re-doing work without inspecting the current state.
- Using a powerful/expensive model for low-value tasks.
- Failing to verify links, files, repository state, website state, or implementation.
- Polishing a broken underlying system instead of fixing the actual failure mode.
- Hiding uncertainty.
- Generic praise or "looks great" without evidence.

> "Which model is the smartest?"

> "Which model/tool/workflow produces the required observable result on the real task, under the real constraints?"

**Priority ≈ Urgency × Consequence × Opportunity Value × Effort × Deadline Proximity × Dependency Impact**

# 14. AI Capability Discovery / Black-Teaming Method

A high-priority durable concept emerged from prior conversations:

## Capability Boundary Probing (CBP)

Instead of asking:

> "Does this product support X?"

Probe the system's **available primitives** and compose them to discover latent/unadvertised capabilities.

Examples of primitive composition may include:

- Frame extraction
- Image generation
- Image transformation
- Cut/crop/edit paths
- Tool chaining
- File manipulation
- Browser/computer interaction
- Multimodal transformations

The key methodological principle:

> A system's declared feature list is not necessarily its true capability boundary.

Capability should be experimentally probed.

## Black-Team methodology

A reusable process:

1. Identify the claimed boundary.
2. Enumerate exposed primitives.
3. Find compositions across primitives.
4. Construct a minimal capability probe.
5. Observe actual output.
6. Search for edge cases.
7. Record whether the capability is:
   - Explicit
   - Composed
   - Accidental
   - Partial
   - Unreliable
8. Re-test under variations.
9. Document the exploit/insight as a capability-discovery finding.

This is framed as legitimate evaluation/research rather than abusing systems.

# 31. AI Reliability Lessons

Several recurring lessons have become durable:

## Lesson 1 — Model claims are not evidence
Always test actual behavior.

## Lesson 2 — A generated artifact can still be wrong
Passing generation does not mean passing validation.

## Lesson 3 — One model should not be its own final judge
Use independent evaluation when stakes justify it.

## Lesson 4 — Deterministic checks are underrated
Schemas, tests, source checks, duplicate detection, and invariants catch classes of errors that language models miss.

## Lesson 5 — Models need explicit role boundaries
Generation, critique, verification, and publication should not blur together.

## Lesson 6 — Repository state is ground truth
When an agent says "done," inspect the filesystem/git/build.

## Lesson 7 — Dangerous functionality requires stronger gates
Deletion, payments, licensing, security, and account state need more verification than prose formatting.
